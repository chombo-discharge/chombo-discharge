A cell key together with the AMR level it was computed on – see cellKeyOf()'s warning.

Two NNCellKeys are equal only if BOTH the level and the cell index match; a coarse- level cell and an unrelated fine-level cell that happen to share the same bare IntVect are correctly kept distinct because their level differs. ◆ NNWalkCell

using ParticleManagement::detail::NNWalkCell = IntVect

A non-level-qualified cell index, distinct from NNCellKey, used where a cell is expressed in a single consistent frame (the query patch's own level).

A separate alias from NNCellKey (which is level-qualified for the cross-level crowding-count map) so the two cannot be passed interchangeably. NNWalkCell is always computed with the query patch's own level's dx, even for a cross-level ghost, so candidates are geometrically comparable to the query in one frame (see cellKeyOf()'s warning).

◆ PositionLocator

using ParticleManagement::detail::PositionLocator = std::function<LevelTiles::LevelAndBox(const RealVect& a_position)>

Locate-by-position callback – see placeMergedParticles().

Returns LevelTiles::LevelAndBox, which is what ParticleContainer::findDestination() already produces: an O(1) point->block query on the realm's LevelTiles tile->box hash, the SAME lookup a ParticleContainer uses internally to route its own particles during remap(), never a linear scan over patches. Going through that one mapping keeps it the single source of truth for "which box owns this position".

The callback itself remains, so this header does not depend on ParticleContainer; only the result type is shared. Call frequency is bounded by the number of MERGE RESULTS this round (not by the number of candidate pairs), so a non-inlined indirect call is an acceptable cost – this is not a hot inner-loop path.

Build a KD partition of a list of particles and return the leaf particle ranges.

Partitions the input particles into at most a_maxLeaves spatial groups ("leaves"). Each split divides the node along the longest bounding-box axis, at the weight median while the node is no wider than a_weightMedianLength and at the count median above that – the same size-dependent rule the whole-patch build uses, and the same one a fixed 'weight' or 'count' setting expresses as a crossover above or below every node's size. Under the weight median the halves carry as nearly equal a weight as possible (differing by at most one physical particle), which may require dividing the median particle itself, in which case a_particleReconcile fixes up the daughters' non-weight members; the count median never divides a particle. This is the partitioning primitive behind super-particle merging: the caller reduces each returned leaf range to a single merged particle.

Implementation note: the tree is built in a flat, reusable per-thread scratch arena (two ping-ponged contiguous particle buffers + a flat range list), so there is no per-node heap allocation, no pointer chasing, and the scratch is reused across calls on the same thread.

Template parameters: P -> Particle type exposing the weight/position data members below P::*weight -> Pointer to the Real data member holding the particle weight P::*position -> Pointer to the RealVect data member holding the particle position.

P must be an AoS-style particle type carrying weight and position as data members – MergeParticle is the one this library provides, and the one every in-tree caller uses. ParticleSoA payload types (ItoParticle, ...) store those two in the container rather than the payload, so pack the columns into such an intermediary AoS structure first.

Parameters
[in]a_particlesInput particles (copied into internal scratch; not modified).
[in]a_maxLeavesMaximum number of leaf nodes (the per-cell target particle count).
[in]a_weightMedianLengthNode size, as a length, at or below which the split plane is the weight median rather than the count median. Negative disables the weight median entirely; a huge value selects it everywhere.
[in]a_capWeightsIf true, divide every input particle heavier than the target leaf weight (total weight / a_maxLeaves) into co-located integer pieces before partitioning, so no single particle can dominate a leaf.
[in]a_splitPositionWhere a split particle's pieces go, given the parent's position. The identity reproduces the parent's position exactly; see KDSplitPlacement for why that is not always what you want.
[in]a_particleReconcileReconciliation callback applied to the two daughters when the median is split.
[out]a_leavesFilled with one {begin,end} pointer pair per leaf.
Warning
The returned ranges alias an internal thread-local buffer that is overwritten on the next call to this function on the same thread. Consume them (reduce each leaf) before calling again.

a_particles is reordered IN PLACE, so each returned leaf's [lo,hi) range is contiguous in the reordered buffer; no particle is ever copied or split synthetically.

A leaf collapses to exactly ONE super-particle at its own weighted centroid, so the number of leaves whose centroid falls in a cell is that cell's post-merge population. That count is tracked live in a per-cell map while splitting, and a split that would push a cell past a_ppc is refused. Splitting takes the heaviest candidate leaf first and stops when nothing may legally be split.

Splits are along the longest real-space axis and are deliberately UNSNAPPED to the grid, so a leaf may straddle a cell face and draw members from either side. The split plane is the count median while the node is wider than a_weightMedianCellWidths cell widths, and the weight median once it is narrower: above that scale a split apportions leaves between cells, which is a question of counts; below it the weight median drives the resulting super-particles toward equal weight.

The quota constrains only leaves that can actually merge. mergeKDCarve() and mergeKDPatch() veto any leaf wider than s_kdMaxLeafExtent and leaves its members behind individually, so such a leaf costs its cell its full member count rather than one particle; the quota therefore does not block splitting it further. As a result a cell can finish slightly above a_ppc when a leaf is both too wide to merge and in a cell already at quota, since both available choices overshoot.

Particles in cells at or below a_ppc are excluded from the partition and emitted as singleton leaves. A singleton never merges (the merge threshold is two members), so an uncrowded cell cannot be drained by a neighbour's merge.

Blindly rejecting that case causes a PERMANENT deadlock (a stable mutual pair proposes to each other identically every round and is rejected every round, forever, since nothing changes to break the symmetry) – so it must be accepted instead. Because BOTH sides of a mutual pair detect the match independently, a deterministic tiebreak (lower-id side performs the accept, higher-id side falls back to the normal reject) is required, or both sides would accept and double-merge the same two particles.
  4. ALL eligible target decisions (plain-argmin and mutual-match alike) are resolved in ONE globally distance-sorted pass across every target this rank is judging (with an id tiebreak) – NOT by iterating targets in whatever order the incoming-proposal list happens to be in. Accepting one target decrements its cell's live count, which can push a DIFFERENT target sharing that cell below threshold; judging targets in arbitrary order makes that outcome depend on arbitrary processing order. Sorting closest-first with a dynamic per-target threshold recheck (mirroring resolveTrivialTier()'s discipline exactly) removes that dependency.
  5. This handles any number of simultaneous suitors for one particle, not just pairwise boundaries – a corner where 3+ patches meet is resolved by this exact same logic, with no special-casing, since every proposal naming a given target funnels into the same "group by target id" step regardless of how many different ranks it came from.
  6. A_maxCellDistance and a_isPositionValid apply here exactly as they do in resolveTrivialTier() – a physical-validity rule, not a coordination one. An incoming proposal that is too far, or whose weighted-centroid position fails a_isPositionValid, is never eligible to be accepted (skipped as though it did not exist for argmin purposes), REGARDLESS of the mutual-match exception in rule 3 – an invalid position is invalid on both sides of a pair, mutual match or not.

Proposals addressed to this rank's own particles arrive from two sources, pooled identically here: proposals received over MPI from other ranks, and this rank's own generateProposals()-produced bucket addressed to itself (an in-process handoff, no network round-trip – see generateProposals()).

Resolve every candidate edge that is safely mergeable with zero cross-rank coordination, and mark which remaining particles have committed to a non-trivial outgoing proposal.

An edge is trivial-tier eligible iff NEITHER the query nor the candidate is boundary-exposed (see Realm::m_particleGhostExposure) – this check happens AFTER finding the true nearest neighbor, never as a restriction on the search itself.

All eligible edges (across every patch this rank owns) are processed in ONE globally distance-sorted order, with a deterministic secondary tiebreak on participant ids – exact distance ties (e.g. true mutual nearest neighbors) are common enough that leaving them to arbitrary iteration/insertion order produces real, observed nondeterminism that cascades into unrelated pairs several hops away.

At the moment each edge is actually processed (not at generation time): re-verify both participants are still alive (lazy invalidation – skip if either was already consumed by a closer edge processed earlier in this same pass); if the candidate is local, re-verify it has NOT, in the meantime, committed to its OWN outgoing (non-trivial) proposal – a purely geometric "exposed" check on the candidate alone is insufficient, since a non-exposed particle's true nearest neighbor can still be a foreign ghost even though the particle itself is unreachable externally; consuming such a candidate trivially anyway is a real double-consumption bug this dynamic recheck closes. Finally, re-verify both participants' CURRENT cell occupancy (reflecting decrements from edges already processed this pass, not the generation-time snapshot) still exceeds the threshold.

On a successful trivial-tier commit: remove both participants from the caller's own valid particle list (conceptually – see a_consumedIDs), decrement both cells' live counts, and record the merge via a_combine/into a_results. On an edge that cannot be resolved trivially, exactly one of two things happens, and the distinction matters:

  • If the candidate is a ghost, OR either participant is boundary-exposed, OR the candidate turned out to already have its own outgoing commitment: mark the query particle as having an outgoing commitment (see a_hasOutgoingCommitment) so generateProposals() can pick it up. In all three cases the candidate genuinely still exists (it just isn't trivially available right now), so a proposal is meaningful – judgeProposals() already has a rule for "target has its own outgoing commitment" (accept only on a mutual match, reject otherwise), and that rule is exactly what should get a chance to run here, not a silent no-op.
  • If the candidate is stale (already consumed – found dead by the lazy-invalidation check above): do NOT mark the query particle as having an outgoing commitment, and do NOT generate a proposal. There is no meaningful id to propose to. Critically, this also means the query particle is NOT marked "busy" – it remains fully available for some OTHER particle to claim as an ordinary trivial candidate later in this same sorted pass, or via a_maxFallbackCandidates below.
